# Isolated Agent dependency payloads

All 32 official dependency recipes support a runner-owned payload
store while keeping dependency metadata, stable launchers and Agent homes in
persistent storage. The recipes do not change `HOME`, `CODEX_HOME`,
`CLAUDE_CONFIG_DIR` or authentication files.

The install and update scripts declare the protocol in their leading comments:

```sh
# memoh-storage-layout: isolated
```

The declaration is part of the recipe bytes covered by both `manifest_digest`
and the artifact digest. It is deliberately not a new manifest key or an
unreferenced artifact file: existing Memoh clients strictly reject those. Old
runners ignore the shell comment and take the compatible version-directory
branch. New runners must validate the declaration before enabling the contract.

| Variable | Contract |
| --- | --- |
| `MEMOH_DEP_HOME` | Persistent dependency metadata directory; never an Agent home |
| `MEMOH_DEP_STORE` | This dependency's payload and package-cache directory; defaults to `MEMOH_DEP_HOME` for old runners |
| `MEMOH_DEP_INSTALL_DIR` | Unique final candidate directory allocated by the new runner; must not already exist |
| `MEMOH_DEP_STAGING` | This operation's staging directory inside the store; absent values use a unique temporary directory |
| `MEMOH_DEP_VERSION` | Requested release; recovery must supply an exact version from its approved desired installation |
| `MEMOH_DEP_RESULT` | Runner-owned result location outside the payload tree |
| `MEMOH_DEP_OPERATION_DIR` | Durable operation receipt directory; generated recipes record their candidate here |
| `MEMOH_DEP_CANDIDATE` | Executable selected by the Server for a frozen `version` health probe |

The five shell recipes (Codex, Claude Code, Node.js, Python and uv) download and
unpack into their own staging directory, verify the reported version and all
declared launchers, and rename the completed tree to the assigned candidate.
`dep_switch` records that absolute candidate path in the operation receipt.

The other 27 recipes share `scripts/dependencies/runtime.py`, generated by
`generate.ts`. They install directly into the unique candidate because venv,
Conda, rustup and launcher wrappers embed absolute paths. That candidate is not
published during installation. After validation the runtime writes the same
operation receipt's `candidate` file; an unsuccessful install removes only its
own candidate. It refuses an existing target, including a target supplied again
for the same version. It never renames an installed venv to another prefix.

In both cases, the Server commits `current` only after its authorization and
transaction checks. `dep_result` keeps entrypoints at
`$MEMOH_DEP_HOME/current/bin/<command>` so callers retain stable paths.

The new branch never overwrites a published installation, enumerates previous
versions, or deletes another operation's staging directory. A new-runner remove
script only reports success; the runner validates and cleans the registered
payload, metadata and caches after commit. It must export the isolated-layout
variables only for recipes that declared this protocol. Older runners retain
their existing home removal and temporary failed-replacement recovery behavior.

npm, uv, micromamba and apt caches use `<store>/cache`. LibreOffice metadata
resolution uses this cache root as well as its actual installation phase. The runner owns cache limits and garbage
collection under its existing dependency lock. Node.js and uv downloads continue
to validate digests obtained from their official release authorities even when
a download mirror is selected. npm installs retain `--ignore-scripts`; Claude
Code's supported native optional package is linked explicitly.

Explicit Node.js, uv, Python, Codex and Claude Code versions must match the
installed executable's version. npm registry responses that change an exact
request fail before installation. Python exact requests bypass selection of the
latest matching interpreter. Update and install share the same publication
contract; reinstall uses the manifest's existing install fallback. A downgrade
is another explicitly requested installation, with no previous-version API.

The generated recipes expose `version.sh`. It executes each declared command
with the recipe's explicit probe arguments (for example `go version` or
`pdftotext -v`) and returns the saved installation resolution. Node and Python
bundles also import every declared module; a working interpreter alone cannot
mark a damaged package tree healthy.

A version identifier is recipe-specific. The shell recipes resolve full
three-component releases. Generated recipes also use forms such as a
four-component LibreOffice version, a Debian epoch encoded with `_`, or a
composite package identifier `0.0.0+<hash>`. The Server must preserve these
canonical identifiers and reject floating requests before management confirms
them. A universal three-component SemVer restriction rejects valid generated
recipes. Conversely, accepting a numeric string by syntax alone does not prove
that a Python minor selector such as `3.13` is an exact target.

Composite npm/Python resolutions persist in `MEMOH_DEP_HOME/resolutions` so a
previously approved package set remains reconstructible after local store loss.
These small metadata files contain no payloads or credentials. Before reuse,
the runtime verifies that package names match the frozen recipe and that their
version-map hash matches the approved composite identifier. A modified mapping
fails before downloads. This metadata does not grant installation permission;
the Server still requires its durable desired installation and frozen recipe.
Only the Server can safely collect unreferenced resolution metadata after
accounting for current desired installations and unfinished confirmations.

## Local verification

Use the Bun version in `.bun-version`:

```sh
bun test test/dependency-recipes.test.ts
bun run registry:lock -- --registry memoh --kind dependencies
bun run registry:validate
bun run registry:publish -- --registry memoh --kind dependencies
bun run dev -- --host 0.0.0.0 --port 5175
```

The HTTP API exposes the newly generated immutable release descriptors and
recipe artifacts. A Memoh development container can use
`http://host.docker.internal:5175`; check the effective port printed by Vite.
Full App integration additionally requires publishing the App registry with
`bun run registry:publish -- --registry memoh`.

The offline recipe tests cover old-runner publication failures, isolated
candidate publication, cache location, preservation of another operation's
staging, refused candidate overwrite, deferred removal, version mismatch and
checksum rejection. The following opt-in smoke uses real upstream downloads and
executes every published launcher after relocation, plus the generated pnpm
recipe and its frozen health action:

```sh
python3 scripts/dependencies/agent-storage-smoke.py --versions \
  node=24.4.1,uv=0.11.8,python=3.13.2,codex=0.154.0,claude-code=2.1.270 \
  --extra-versions pnpm=12.4.1 --simulate-store-loss
```

It creates its own disposable directory, records commands and timings, then
removes only its local payload store and reinstalls the same versions. It keeps
persistent homes and entrypoints to exercise dangling-link recovery. This is a
recipe smoke; Memoh API authorization, database persistence, actual workspace
rootfs deletion, automatic repair and UI verification require the Memoh
integration suite and real development environment.
